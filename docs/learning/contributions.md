# 个人贡献规划与验收条件

## 定位

项目名：RailTicket 票务交易系统。

定位：基于开源 12306 学习交易业务，并通过环境复现、缓存保护和消息异常处理形成自己的工程改进。业务领域与已有知识点相匹配，避免只改名称、包名和页面。

当前个人工作包括仓库整理、学习导航、本机中间件与运行配置，以及基础接口验证；下面列出的三项增强功能仍需按验收条件完成。

## 上游已有能力

- 用户、购票、订单和支付业务模块。
- Redis 缓存组件、Redisson 互斥重建和双重检查。
- Lua 余票令牌处理及取消后的回滚逻辑。
- RocketMQ 延迟关单、幂等组件。
- Maven 多模块、聚合版与微服务版启动方式。

具体以源码和运行验证为准。以上不能直接表述为个人原创实现。

## 建议优先完成的三个改进

| 优先级 | 待实现内容 | 需要回答的问题 | 验收证据 |
| --- | --- | --- | --- |
| P0 | Docker Compose 环境复现（本机已跑通，可移植交付待完善） | 服务如何发现彼此？数据存在哪里？启动顺序是否等于服务已就绪？配置如何传入？ | 环境说明、健康检查结果、全新环境部署记录、一次业务演示 |
| P1 | 热点缓存重建保护增强 | 锁等待或数据库加载变慢时，如何限制等待时间和并发回源？何时允许降级？ | 实现提交、热点缓存失效实验、数据库查询次数和延迟对比 |
| P1 | 超时关单的异常恢复 | 数据库释放成功但 Redis 恢复失败时如何发现和恢复？重复消息是否导致重复释放？ | 明确状态与重试规则、故障注入记录、重复投递验证、库存核对结果 |

缓存降级策略需要先按业务定义可接受的数据新鲜度；消息补偿需要先明确业务幂等键和状态转换。具体方案在读懂现有代码、建立运行基线后再设计。
